### 一、 静态装配期：`main` 函数里的“三连环组装”

在 `main.cpp` 中，三个组件通过 `std::bind` 像接力赛跑一样把函数指针（回调接口）牢牢地咬合在一起：

```text
  【高层业务】                  【中间网关层】                【传输层底座】
ProcessWebBusiness  ──注入──►   HttpCodec    ──注入──►   TcpServer
 (处理干净的HttpRequest)       (处理Buffer切包)           (只管收发原始字节)

```

1. **第一环（业务注入网关）**：
`HttpCodec http_codec(ProcessWebBusiness);`
`HttpCodec` 睁开眼，手里就拿到了 `main` 函数里那个负责写核心动态网页、API 路由逻辑的 `ProcessWebBusiness` 函数指针。
2. **第二环（网关注入底座）**：
`server.setMessageCallback(std::bind(&HttpCodec::OnMessage, &http_codec, ...));`
`TcpServer` 睁开眼，它根本不知道什么是 HTTP 协议，但它的肚子里存下了 `HttpCodec::OnMessage` 的地址。

### 二、 动态运行期：数据洪峰触发的“物理流向”

当客户端（浏览器）通过网络发送了一个完整的或残缺的 HTTP 报文时，底层的 `epoll_wait` 惊醒，多线程反应堆（SubReactor）正式开始咆哮，触发了你所描述的回调链路：

```text
 浏览器发送字节流 ──► [内核缓冲区]
                          │
                          ▼ (Epoll 惊醒)
 1.【传输层底座】 TcpConnection::HandleRead() 
    └─ 狂暴抽空内核缓冲区，全部塞进输入缓冲区 `Buffer`。
    └─ 叩响：conn->message_callback_() 
          │
          ▼ (触发回调)
 2.【传输层底座】 TcpServer::OnMessage(conn, buf) 
    └─ 它说：“我手上有个通用插槽 message_callback_，我直接调用它。”
          │
          ▼ (由于在 main 中做了解耦绑定，顺藤摸瓜跨进应用协议层)
 3.【协议网关插件】 HttpCodec::OnMessage(conn, buf) 
    └─ 它拿到连接体内挂载的专属状态机 `HttpContext`。
    └─ 调用 `ctx->ParseRequest(buf)`，利用状态机开始抠索 `\r\n`，剔除大小写差异。
    └─ **特判A（半包）**：发现数据没传全。直接退出函数，不消费 Buffer，静待下一次 Epoll 唤醒。
    └─ **特判B（全包）**：状态机走到 `kGotAll`，说明成功剥离出了干净、结构化的 `HttpRequest`！
    └─ 叩响：http_callback_(conn, ctx->GetRequest()) 
          │
          ▼ (触发回调)
 4.【应用层业务】 main.cpp :: ProcessWebBusiness(conn, req) 
    └─ 这里就是真正的“应用层业务回调函数”！
    └─ 开发者面对的不再是恶心的原始 Buffer 字节，而是干干净净、Key 全转成小写的 `req` 对象。
    └─ 根据 `req.path` 拼装好一堆 `HTTP/1.1 200 OK...` 的字符串。
    └─ 调用 `conn->Send(response)` 顺着原路把响应喷回给传输层发送缓冲区并推向网络。

```

### 三、 为什么不让 `TcpServer` 直接认识 `HttpCodec`？（解耦美学）

你可能会想，既然流向这么明确，为什么不在 `TcpServer.cpp` 里面直接 `#include "HttpCodec.h"`，然后硬编码调用 `HttpCodec::OnMessage`？

这就是 **控制反转（IoC）** 和 **依赖倒置** 的工业级工程美学：

* **如果强耦合**：你的 `TcpServer` 内部写死了 HTTP 逻辑，那这个网络库就彻底报废了——它一辈子只能做 HTTP 服务器。如果你明天想用它做《王者荣耀》的游戏战斗服（基于私有二进制协议），或者做 **高性能 RPC 节点（基于 Protobuf）**，你必须把 `TcpServer.cpp` 底层大改一遍。
* **你现在的满血设计**：`TcpServer` 只认一个代号叫 `MessageCallback` 的通用万能插槽。
* 如果 `main` 注入了 `HttpCodec`，它就是 Web 服务器；
* 如果 `main` 注入了 `RpcCodec`，它摇身一变就成了分布式 RPC 算力节点；
* 如果 `main` 注入了 `GameCodec`，它瞬间就成了游戏网关。

## 🚀 阶段六架构满血进化：面向未来的“三层物理去耦”重构

在阶段六的初期版本中，虽然实现了状态机拆包，但 `main.cpp` 依然直接持有 `TcpServer` 并硬编码注入 `HttpCodec::OnMessage`，导致高层业务与网络底座处于“半粘连”状态。

为了实现真正的工业级架构弹性，本阶段进行了一次**面向通用协议、控制反转（IoC）的满血重构**。核心改变在于两点：
1. **引入 `HttpServer` 门面层**：彻底承接、包裹住 `TcpServer` 与 `HttpCodec`，对外提供纯粹的协议级视图。
2. **剥离 `HttpHandler` 独立业务层**：将核心的动态网页渲染、API 路由分发代码移出 `/app` 主逻辑，打造独立的、只吃结构化数据的纯业务处理器。

### 一、 进化后的静态装配线：三层物理隔离（IoC 依赖注入）

重构后，各个组件之间的耦合关系被彻底斩断。组件的组装不再依赖 `main` 函数里的“内脏拼接”，而是采用标准的**门面模式（Facade Pattern）**与**依赖注入（Dependency Injection）**接力：

```text
  【高级应用层】               【协议门面层】               【底层编解码】             【传输层底座】
    main.cpp     ──注入──►    HttpServer    ──中转──►    HttpCodec    ──监听──►   TcpServer
 (纯粹的引擎点火)            (管理服务器门面)             (专门状态机切包)          (只管非阻塞IO字节)
        │                                                     ▲
        └───────────────── 动态依赖注入 (SetHttpCallback) ──────┘
                     (将 app::HandleHttpRequest 注入编解码器)

```

1. **传输层回归纯粹（`TcpServer`）**：
不感知任何 HTTP 报文，只负责多线程线程池（Multi-Reactor）调度、套接字非阻塞读写，并将薅到的原始字节打入 `Buffer`。
2. **协议中转门面（`HttpServer`）**：
作为中央枢纽，其构造函数极其清爽，仅接收端口、线程数等纯网络参数。在内部，它通过 `std::bind` 将 `TcpServer` 的原始数据接收事件代理给自己的 `OnConnectionMessage` 拦截点。
3. **面向未来的注入机制（`SetHttpCallback`）**：
`HttpServer` 暴露了公开的 `SetHttpCallback` 门面接口。当 `main.cpp` 调用该接口传入纯业务函数时，`HttpServer` 顺藤摸瓜，将该回调**接力空投**到内部 `HttpCodec` 的 `http_callback_` 槽位中。
* **工程意义**：彻底丢弃了在初始化列表硬捆绑的僵化设计。未来如果想更换业务路由，或者将架构扩展成 `RpcServer`、`WebsocketServer`，只需扩展对应的门面中转接口，引擎底座无需改动哪怕一行代码。

### 二、 进化后的动态运行期：像素级全链路数据流向

当本地浏览器敲下 `127.0.0.1:8080` 轰炸服务器时，数据的物理流向完成了一次极其丝滑的、跨越三层架构的完美闭环：

```text
 客户端 (浏览器) 
       │  (1. 物理喷射 HTTP 原始字节流 `GET / HTTP/1.1\r\n...`)
       ▼
 ┌──────────────────────────────────────────────────────────────────────────────────┐
 │ 【网络传输层】 TcpServer (MainReactor 接入连接 -> 轮询分发 -> SubReactor 专属线程)     │
 └──────────────────────────────────────────────────────────────────────────────────┘
       │  (2. 子线程 Epoll 惊醒，HandleRead() 非阻塞薅空内核缓冲区，灌入传输层 `Buffer`)
       ▼
 ┌──────────────────────────────────────────────────────────────────────────────────┐
 │ 【网路/协议中转点】 HttpServer::OnConnectionMessage(conn, buf)                     │
 └──────────────────────────────────────────────────────────────────────────────────┘
       │  (3. 门面层拦截，原封不动将原始字节缓冲区接力给专属状态机)
       ▼
 ┌──────────────────────────────────────────────────────────────────────────────────┐
 │ 【协议编解码层】 HttpCodec::OnMessage(conn, buf)                                   │
 └──────────────────────────────────────────────────────────────────────────────────┘
       │  (4. 状态机高效吞噬字节。半包则静待下次 Epoll；全包则 GotAll() 剥离出干净的 HttpRequest)
       ▼
 ┌──────────────────────────────────────────────────────────────────────────────────┐
 │ 【独立应用业务层】 app::HandleHttpRequest(conn, req)                              │
 └──────────────────────────────────────────────────────────────────────────────────┘
          (5. 坠入业务层！开发者不再面对恶心的 Buffer 字节，而是干干净净的结构化对象)
          (6. 执行高级路由分发：)
          ├── 匹配 `req.path == "/"`       -> 组装核心动态 HTML 网页报文
          ├── 匹配 `req.path == "/api/status"` -> 回喷标准的后端 JSON 状态报文
          └── 边缘特判（如 `/favicon.ico`）  -> 404 错误安全兜底保护
          │
          ▼
 交付传输层：调用 `conn->Send(response)` 异步写回缓冲区，数据原路回流，浏览器完美渲染输出！

```

### 三、 生产级多线程装甲加固：`Shutdown` 跨线程安全防线

在多线程 Reactor 架构中，一个隐藏极深的“隐形炸弹”是**对象生命周期的跨线程撕裂**：如果业务层 `HttpHandler` 在第三方工作线程中执行完毕后直接原地更改连接状态或调用物理断开，由于其不属于该连接绑定的专属 Sub-Reactor 子线程，会瞬间引发严重的跨线程数据竞争、踩野指针导致进程暴毙。

为此，本阶段对 `TcpConnection::Shutdown()` 进行了硬核加固：

```cpp
void TcpConnection::Shutdown() {
    if (state_ == kConnected) {
        state_ = kDisconnecting;
        
        // 🌟 跨线程安全装甲：强制把物理断开动作揉成 Lambda 表达式
        // 配合 `shared_from_this()` 强行延长连接对象的寿命，安全空投到连接绑定的专属子线程中调度执行！
        loop_->QueueInLoop([this, guard = shared_from_this()]() {
            if (!channel_->IsWriting()) {
                ::shutdown(conn_fd_, SHUT_WR); // 在专属子线程中安全切断写端
            }
        });
    }
}

```

### 四、 阶段总结与架构复盘

经过此次重构，项目目录演化得层次分明、极具工业美感：

* `/src/net/`：纯粹的 Reactor 网络底座（只管非阻塞 IO 与线程调度）。
* `/src/http/`：纯粹的协议关卡（`HttpServer` 门面与 `HttpCodec` 状态机，只管破译协议）。
* `/app/`：纯粹的业务大本营（`main.cpp` 点火，`HttpHandler` 写网站逻辑与路由，只管消费数据）。
